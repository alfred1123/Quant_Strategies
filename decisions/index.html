    43 Frontend baseline: Node 24 + React Router 8 + ESLint 10 React Router v8 removed the react-router-dom re-export package, so every import now comes from react-router (declarative mode uses no react-router/dom APIs). v8 requires Node ≥ 22.22 and React ≥ 19.2.7 and ships ESM-only. ESLint 10 was taken at the same time to clear the transitive minimatch/brace-expansion advisory that ESLint 9 pinned. Result: npm audit --audit-level=high exits 0, so the audit gate in both workflows passes. frontend.md
    44 market_data/ owns MARKET_DATA end-to-end Every module in quant/data/ is a data-access adapter — two DbGateway caches plus vendor clients — and the orchestration that uses them lives in a domain package (quant/strategy/backtest_service.py consumes BacktestCache; quant/trade/ consumes InstrumentCache). PriceBarService owns the freshness rule, gap repair and the fail-closed decision, so putting it in data/ would mix layers. quant/market_data/ holds repo.py (MARKET_DATA SP wrappers), fetcher.py (public ccxt OHLCV — deliberately not on CcxtTradeGateway, since bars must not depend on a user's API credentials) and service.py (policy), mirroring how quant/trade/ owns TRADE. Interval arithmetic is pure and needed by both bars and the scheduler, so it sits in quant/shared/intervals.py rather than either domain — with no I/O: resolving TM_INTERVAL_ID to a period is RedisRefData.get_interval_period, alongside resolve_app_id / resolve_queue_status_id, so every REFDATA lookup stays in one place. Amends #31. scheduler-price-bars.md, pipeline.md
    45 Live signals price off the venue's own bars — venue decides, not schedule The provider/exchange split follows how data is used, not how the apply was triggered: research (backtest, dry-run) reads provider history (daily, 10-year ranges — what Glassnode/Yahoo are for); a live apply reads MARKET_DATA.PRICE_BAR from the exchange it executes on whenever that exchange serves market data, manual or scheduled. The schedule only sets the bar interval — no schedule means daily, resolved from REFDATA.TM_INTERVAL via RedisRefData.resolve_interval_id(timedelta(days=1)), never hardcoded. The provider path survives in live apply only for brokers with no market-data venue (Futu equities), where the provider series is the only one that exists. Consequence: manual and scheduled applies of one deployment read the same series, so attaching a schedule changes cadence, never input data; the fitted-on-provider vs traded-on-exchange divergence applies to all live signals and is traceable via ApplyReport.bar_source. Supersedes the earlier schedule-based switch in LiveApplyOrchestrator._resolve_signal_source. scheduler-price-bars.md, live-trading-promotion.md
    46 A missed schedule catches up one interval per pass, at today's price A backlog drains through repeated ticks rather than a jump to the current boundary: ScheduleTickRunner.run_interval advances a due deployment by exactly one interval per pass, reading NEXT_SCHEDULED_TS off the row instead of recomputing from now(), so the schedule keeps its original phase however late the tick ran. Every pass leaves a DEPLOYMENT_SCHEDULE_STATUS row, and that per-slot history is the only record of what downtime cost — collapsing the backlog would reach the same position and erase it. Catch-up does not replay the missed period: load_window derives its window from now(), so each pass computes today's signal and an order fills at today's price. Replay is impossible in principle (an order placed now fills now) and undesirable in practice (a stale signal is worse than a current one), even though load_window(now=...) could reconstruct it and the missed bars are in PRICE_BAR. Repeated applies converge rather than stack, because intended_side compares the signal against the live broker position and returns HOLD once it already matches — so a three-day gap is one trade plus two no-ops. Recovering the P&L of a missed slot is out of scope here and belongs to reconciliation. scheduler-price-bars.md
    47 SOURCE_APP_ID belongs in the PRICE_BAR key — a bar is a fact from a venue MARKET_DATA.PRICE_BAR is keyed (INTERNAL_CUSIP, TM_INTERVAL_ID, SOURCE_APP_ID, BAR_TIMESTAMP). Decision #21 makes one product cover a traded pair across brokers, so btcusdt.crypto carries INST.PRODUCT_XREF rows for both Bybit and Binance. Keying without the source let whichever venue wrote a timestamp first own it: the loser's insert raised unique_violation, PriceBarService._insert absorbed it as a benign race, and that deployment priced its signal off the other exchange's prints — while SP_GET_PRICE_BAR_COVERAGE, also unscoped, reported the first venue's bars as the second's freshness so it never even fetched. The result was a silently blended series whose composition depended on which deployment ran first. Both read procedures therefore take IN_SOURCE_APP_ID, and PriceBarRepo / PriceBarService.read_bars require it. This is what lets the table serve as one source of truth for backtest and trade: a paid backfill provider becomes another SOURCE_APP_ID beside live bars rather than a collision, and a backtest pinned to a source reproduces. Prices are not expected to match across sources — separate order books, and provider bars differ again in session convention; the guarantee is consistency within a series, not equality between them. scheduler-price-bars.md §4.1
    48 Continuity is repaired explicitly; the live lookback only maintains a rolling window ensure_fresh refills [newest - period × (lookback - 1), newest] and nothing else, and lookback is a bar count (max_window × 3 + 60), so what it covers in wall-clock time depends on the interval: 120 daily bars survive a 10-day outage, 120 hourly bars only five days. Bars older than the window are never requested again, so a longer outage leaves a permanent hole. Trading is unaffected — load_window needs only the window and fails closed if it cannot complete it — but the table is therefore a rolling window maintained as a side effect of trading, not a continuous history, which is not good enough for backtest. PriceBarService.backfill(...) takes an explicit range and fills every hole in it; find_gaps(...) answers the same question read-only. Backfill inverts the fail-closed rule the module otherwise follows: on the trade path a hole must stop the run, but during a repair a hole is ordinary (pre-listing history, or past what the venue retains) and aborting would discard the bars that were recoverable — so it reports BackfillResult.unfilled instead. Separately, catch-up bars are accurate: a closed candle is immutable, so one fetched ten days late is identical to one fetched at the boundary. Depth is bounded by the venue's fetch_ohlcv retention, which is why a paid provider under its own SOURCE_APP_ID (#47) remains the answer for deep history. scheduler-price-bars.md §4.6
    49 A deployment may only be scheduled on the cadence its strategy was fitted on Decision #45 settled that the schedule sets the bar interval a live signal reads; the consequence is that choosing a cadence is choosing an input series, not a clock. Every backtest fits on daily bars, so the hourly option in the schedule dropdown offered to run daily-fitted parameters over hourly bars. That combination is the worst available failure mode: it is completely silent — a 20-period band computes fine over 20 hourly bars, intended_side returns a real action, the order places, and the execution diary looks healthy, so real money moves on statistics no backtest ever produced and nothing reports a problem. quant/trade/schedule_policy.py now refuses any schedule_tm_interval_id outside schedulable_interval_ids(refdata) with 400 on create and update, naming both cadences; null (manual) always passes, since manual prices off the fitted daily interval. The allowed set is resolved through the REFDATA cache, never hardcoded: the module states the fitted period (FITTED_BAR_PERIOD = timedelta(days=1)) and RedisRefData.resolve_interval_id supplies the id, the same route an unscheduled apply takes under #45 — so a renumbered TM_INTERVAL moves the guard with it, and FITTED_BAR_PERIOD is the single line that widens when multi-interval backtests land. Rendering an interval's name in the rejection is RedisRefData.interval_label() (new, beside resolve_interval_id / get_interval_period), keeping every TM_INTERVAL lookup inside the class that owns the snapshot per #44 rather than letting the trade module read raw rows. Two deliberate edges: an update validates only the value the caller sets, never the stored one, so a row whose cadence predates the rule stays reachable by the kill switch (refusing that PATCH would mean refusing to disable it); and GET /api/v1/trade/schedule-options publishes the set so DeploymentDialog and ScheduleCell grey out the rejected cadences instead of hiding them — a missing option reads as a missing feature, a disabled one plus its helper line teaches that the schedule chooses the bars. scheduler-price-bars.md §3.1.1, api.md
    50 Bar capture is subscribable, and a subscription has no owner Amends #5 ("only products with active deployments get bars stored"), which was aimed at avoiding a bulk ingest of every product and was never asked about research. The coupling it created was incidental — bars are public, CcxtBarFetcher is deliberately keyless, and PriceBarService already had sync / backfill / find_gaps / read_bars — so what was missing was a second answer to which instruments matter, not new machinery. MARKET_DATA.BAR_SUBSCRIPTION is that answer: (INTERNAL_CUSIP, TM_INTERVAL_ID, SOURCE_APP_ID), which is PRICE_BAR's key minus BAR_TIMESTAMP, soft-versioned like DEPLOYMENT so the history records which series the platform was capturing when. The motivation is not convenience: #47 §7.7 records live parameters fitted on Glassnode daily data now pricing against Bybit prints, and capturing a venue's bars before committing capital is what lets a strategy be fitted on the series it will actually trade. A subscription is platform-wide, not per user — the design proposed one row per user with a DISTINCT in the warmer, on the grounds that unsubscribing should not stop somebody else's capture; rejected, because a bar is a shared fact and per-user rows model private ownership of something nobody owns. One row per series instead, with UQ_BAR_SUBSCRIPTION_OPEN enforcing it. The table also carries no USER_ID, a deliberate exception to the audit convention of #12: SP_INS_BAR_SUBSCRIPTION still passes IN_USER_ID to CORE_INS_LOG_PROC, so CORE_ADMIN.LOG_PROC_DETAIL answers who changed a series while the version window here answers when — a column would be a second copy of one fact, free to disagree with the log, and no API or UI ever read it. The accepted cost is that disabling stops capture for everyone, which is why the list is unscoped and every row is visible to every signed-in user. Extends #44 to the warm loop: BarWarmer moves from quant/trade/scheduler/warm.py to quant/market_data/warm.py and takes InstrumentSource implementations, because "which instruments matter" stopped being a deployment question the moment it had a second answer. The one-way rule gets stronger — quant/market_data/ knows a protocol, and DeploymentInstrumentSource in quant/trade/bar_source.py supplies the traded half. The two are unioned, not kept in step: auto-subscribing on deploy would force an unanswerable question on every stop (was that capture the deployment's, or wanted in its own right?). Subscriptions are validated on write — product xref present, app resolvable to a ccxt venue — turning three silent per-tick warm failures into one 400. Backfill is exposed as an explicit, reported operation per #48; nothing crawls, and BACKFILL_FROM_TS is intent the UI displays, not progress. The backtest seam that consumes these bars landed as #51. market-data-capture.md
    51 A strategy is fitted on the series it will be traded on, and refuses rather than substitute The consequence #50 was built for. fetch_df had one path — getattr(quant.data.sources, app["class_name"]) — and no exchange has such a class, so selecting Bybit as a backtest data source raised AttributeError: module 'quant.data.sources' has no attribute 'Bybit': the one venue a crypto deployment executes on was the one venue it could not be fitted on, and the dialog quietly showed a Yahoo BTC-USD beside a Bybit account. fetch_df now branches on REFDATA.APP.IS_EXCHANGE_IND and reads PriceBarService.read_bars, whose DataFrame is already shape-identical to the provider's, so no indicator or performance code changed. Picking the venue is pinning SOURCE_APP_ID per #47 — no mode flag, no second request field. Three properties are deliberate. The BT.API_REQUEST cache is bypassed, because PRICE_BAR is the store and a copy is a second version of one fact, free to diverge. Nothing crawls: a backtest never triggers a fetch, since capture is a standing decision made on the Market data page per #48, so an uncovered range is an error naming the covered one rather than a five-year exchange crawl on someone's behalf — and never a short series returned under the requested label, which is the silent substitution the whole change exists to end. The daily interval is resolved, not hardcoded: BACKTEST_BAR_PERIOD states the period and REFDATA supplies the id, the route #49 established. Factors keep their own source — the question #50 left open, now closed against live's rule: live routes every symbol to the exchange because mixing series is fatal with capital at risk, while a ^VIX-filtered crypto backtest is legitimate research and no exchange serves ^VIX, so f.data_source or req.data_source stands and a factor inheriting a venue it has no INST.PRODUCT_XREF row on is told to name its own source. Separately, the dry run was fixed to read the live series: it called compute_latest_position without a bar_loader while the apply passed one, so a preview could report HOLD off provider bars and the order that followed BUY off exchange bars, neither malfunctioning. LiveApplyOrchestrator._resolve_signal_source moved to bar_source.resolve_signal_source and both callers share it; a dry run predates its schedule so it falls through to daily, and DryRunReport.bar_source reports the venue beside ApplyReport's.
