| 46 | **A missed schedule catches up one interval per pass, at today's price** | A backlog drains through repeated ticks rather than a jump to the current boundary: `ScheduleTickRunner.run_interval` advances a due deployment by exactly one interval per pass, reading `NEXT_SCHEDULED_TS` off the row instead of recomputing from `now()`, so the schedule keeps its original phase however late the tick ran. Every pass leaves a `DEPLOYMENT_SCHEDULE_STATUS` row, and that per-slot history is the only record of what downtime cost — collapsing the backlog would reach the same position and erase it. Catch-up does **not** replay the missed period: `load_window` derives its window from `now()`, so each pass computes today's signal and an order fills at today's price. Replay is impossible in principle (an order placed now fills now) and undesirable in practice (a stale signal is worse than a current one), even though `load_window(now=...)` could reconstruct it and the missed bars are in `PRICE_BAR`. Repeated applies converge rather than stack, because `intended_side` compares the signal against the live broker position and returns `HOLD` once it already matches — so a three-day gap is one trade plus two no-ops. Recovering the *P&L* of a missed slot is out of scope here and belongs to reconciliation. | [scheduler-price-bars.md](design/scheduler-price-bars.md) |
| 47 | **`SOURCE_APP_ID` belongs in the `PRICE_BAR` key — a bar is a fact *from a venue*** | `MARKET_DATA.PRICE_BAR` is keyed `(INTERNAL_CUSIP, TM_INTERVAL_ID, SOURCE_APP_ID, BAR_TIMESTAMP)`. | 48 | **Continuity is repaired explicitly; the live lookback only maintains a rolling window** | `ensure_fresh` refills `[newest - period × (lookback - 1), newest]` and nothing else, and `lookback` is a **bar count** (`max_window × 3 + 60`), so what it covers in wall-clock time depends on the interval: 120 daily bars survive a 10-day outage, 120 hourly bars only five days. Bars older than the window are never requested again, so a longer outage leaves a permanent hole. Trading is unaffected — `load_window` needs only the window and fails closed if it cannot complete it — but the table is therefore a rolling window maintained as a side effect of trading, not a continuous history, which is not good enough for backtest. `PriceBarService.backfill(...)` takes an explicit range and fills every hole in it; `find_gaps(...)` answers the same question read-only. Backfill **inverts the fail-closed rule** the module otherwise follows: on the trade path a hole must stop the run, but during a repair a hole is ordinary (pre-listing history, or past what the venue retains) and aborting would discard the bars that *were* recoverable — so it reports `BackfillResult.unfilled` instead. Separately, catch-up bars are *accurate*: a closed candle is immutable, so one fetched ten days late is identical to one fetched at the boundary. Depth is bounded by the venue's `fetch_ohlcv` retention, which is why a paid provider under its own `SOURCE_APP_ID` (#47) remains the answer for deep history. | [scheduler-price-bars.md](design/scheduler-price-bars.md) §4.6 |

| 50 | **Bar capture is subscribable, and a subscription has no owner** | **Amends #5** (*"only products with active deployments get bars stored"*), which was aimed at avoiding a bulk ingest of every product and was never asked about research. The coupling it created was incidental — bars are public, `CcxtBarFetcher` is deliberately keyless, and `PriceBarService` already had `sync` / `backfill` / `find_gaps` / `read_bars` — so what was missing was a second answer to *which instruments matter*, not new machinery. `MARKET_DATA.BAR_SUBSCRIPTION` is that answer: `(INTERNAL_CUSIP, TM_INTERVAL_ID, SOURCE_APP_ID)`, which is `PRICE_BAR`'s key minus `BAR_TIMESTAMP`, soft-versioned like `DEPLOYMENT` so the history records which series the platform was capturing when. The motivation is not convenience: #47 §7.7 records live parameters fitted on Glassnode daily data now pricing against Bybit prints, and capturing a venue's bars **before** committing capital is what lets a strategy be fitted on the series it will actually trade. **A subscription is platform-wide, not per user** — the design proposed one row per user with a `DISTINCT` in the warmer, on the grounds that unsubscribing should not stop somebody else's capture; rejected, because a bar is a shared fact and per-user rows model private ownership of something nobody owns. One row per series instead, with `UQ_BAR_SUBSCRIPTION_OPEN` enforcing it. Adding OUT columns changes a signature, so the release drops the old ones first — `CREATE OR REPLACE` cannot, and re-applying a body across a changed OUT list is what killed the 2026-08-16 deploy (#60). `SP_INS_PRODUCT_XREF` also resolves a NULL id to the *open* row for `(PRODUCT_ID, APP_ID)` rather than allocating, so correcting a mistyped symbol versions the mapping instead of colliding with `UQ_PRODUCT_XREF_CURRENT`. **Instruments are unowned.** A product is a shared platform fact exactly as a bar subscription is: everybody sees one instrument list and trades against the same rows, so there is nothing for an owner to scope and no ownership filter on any read or write. `USER_ID` is audit and is never read back. Signed-in is the whole check on `POST /api/v1/inst/products`. Restricting administrative changes to certain groups is **deferred** — a real decision, to be taken when there are groups to restrict to, and deliberately not pre-empted by a flag, role check or placeholder that would have to be designed twice. Two known limits, both stated rather than papered over: the two writes are not one transaction (each `CALL` commits), so a rejected xref leaves a product listed nowhere and the retry is a 409 naming it; and bulk vendor import remains unbuilt, so seeding a whole venue's catalogue is still a Liquibase seed changeset (#23). **Amended on review — validation is not the database's job, and soft-versioning stays.** The first cut also put required-field checks, a duplicate-cusip lookup that named the owning `PRODUCT_ID`, a product-exists check and a vendor-symbol clash check into the two procedures. All of it is removed. Restating a schema rule in plpgsql is a second copy to keep in step with the DDL, and it buys nothing a caller can act on that the constraint name does not.
